# tools — checking the site without opening a browser yourself

None of this ships. It is here so the next person to touch the site can see
what they changed instead of hoping. Every bug in `super-ouissy.js` was found
by running these, not by reading the code.

## Running them

```
python3 -m http.server 8899          # from the repo root
cd tools && npm i playwright-core    # once
node regress.js                      # then any script below
```

Two of the chapters are WebGL now — the book intro and the apocalypse — so
launch Chromium with `--use-gl=swiftshader --enable-unsafe-swiftshader` and
**not** `--disable-gpu`, or `THREE.WebGLRenderer` has nothing to draw into.
SwiftShader is software rendering and paints about one frame a second in
here, so drive the apocalypse with `__apLoop(false)` and `__apPump` rather
than waiting on the real loop, and drop the render scale with
`__apQuality(2)`. Anything measured against the wall clock in here is
measuring the container.

Chromium is at `/opt/pw-browsers/chromium-1194/chrome-linux/chrome`. Google
Fonts is blocked by the egress proxy, so every script aborts non-localhost
requests and navigates with `domcontentloaded` — without that the page never
fires `load`. Press Start 2P and Great Vibes fall back to system faces in
these runs; that is the harness, not the site.

## What each one does

| script | what it tells you |
|---|---|
| `realplay.js` | **run this one.** Plays the game the way a person does — clicks through, waits, and looks at what is actually on the canvas — on all three difficulties. Every other suite drives the game itself and is therefore blind to anything wrong with the requestAnimationFrame path, which is how a bug that left the entire game rendering nothing got past 66 green assertions. |
| `quest.js` | **the adventure, checked as a graph.** Walks every node from the title, and clicks all four routes through to their endings. Asserts no node is a dead end, no node is a fail state, all four routes are distinct in the nodes and scenery they use, and the two endings are different. Two dead-end nodes with a *Restart* overlay lived on the live site through several passes because nothing here had ever looked at the story graph. |
| `hvplay.js` | **the three things you can now do in the adventure, played.** The graph suites walk the story by clicking buttons and are therefore blind to all of it: a mechanic that never completed, or completed into the wrong node, leaves both of them green. Plays the stones, all three bridge sections and the orchard well and badly, and checks each lands in the two different places the writing describes. Also asserts the thing that must never stop being true — that every one of those nodes keeps its own buttons on screen for the whole mechanic, so none of it can ever be stuck — plus the keyboard and what survives a reload. Note that requestAnimationFrame is ~3fps in here, far too coarse to hit a timing window through the real loop, so it drives `hvPlayPress`/`hvPlayStep` on a synthetic clock. |
| `hvperf.js` | **what the adventure costs per frame.** Wall-clock frame rate means nothing in here (requestAnimationFrame runs at ~3fps and measures the container), so this times `hvPaintFrame` itself over 300 calls on the heaviest scenes with the loop stopped, against the 16.7ms a 60fps frame allows for *everything*. It found the fog costing 7.2ms a frame — 43% of the budget, 19x the next scene — because `blob` sets a fill colour and fills one pixel at a time, and the fog is three bands of five 52-pixel blobs redrawn every frame: about 34,000 canvas calls. Also reports the one-off scene repaint. |
| `deploycheck.js` | **what a deployment would actually serve.** Exports the committed tree with `git archive` into a clean directory, serves it on a plain static server and loads it — reporting every request, every 404, every page error, and whether the adventure and its score actually came up. The bug it exists for: a file that works locally because it is sitting in the working tree but was never committed, or was committed and then excluded by `.vercelignore`. Locally everything is green; on the preview URL the page is blank. Run it as `git archive HEAD \| tar -x -C /tmp/clean && (cd /tmp/clean && python3 -m http.server 8901 &) && node deploycheck.js`. Google Fonts failing is this container's egress proxy, not the site. |
| `ostrender.js` | **renders the score to a .wav so it can be listened to.** `node ostrender.js sunset 30 out.wav`, or `--all` for a table of every cue. Swaps the live AudioContext for an OfflineAudioContext and runs ost.js's own generator into it, so what comes out is the real music rather than a reimplementation of it. The trap it exists for: a synth score that throws inside a note scheduler fails *silently* — every oscillator after the throw simply never starts, the page reports nothing because it is inside a try/catch, and the game plays in total silence while every "the music is on" assertion passes. |
| `osttune.js` | **whether the score plays the right notes.** Renders each cue's melody alone, finds the pitch of every note that comes out with a Goertzel bin, and compares it to what ost.js says that cue's theme should be — 71 notes across the score. Also checks the one relationship the whole thing is built on (the lantern path is the blossom park's relative minor) as arithmetic, and that the ridge, the bridge and the orchard really do withhold the theme, because the writing depends on them doing so. `ostrender.js` proves the cues make *sound*, which a score transposed by a fourth would also pass. |
| `hvvoiceshot.js` | screenshots an adventure node at a chosen second, so a line of dialogue can be caught mid-conversation rather than at rest. |
| `bearzoom.js` | the bears, magnified, on the grounds they actually stand on. Guessing at a 66-pixel-wide animal from a screenshot is how three rewrites in a row came out looking like rocks; every fault that mattered — the rim light lying across the back like a plank, two legs where there should be four, a head with a seam — was invisible at game size and obvious at 5x. |
| `pairzoom.js` | the two of them, magnified, in daylight and at night, across the walk cycle. For looking at the sprites rather than guessing: the first version's shadow swallowed both pairs of boots and took the whole walk with them, which is invisible at 1.5x and obvious at 5x. |
| `hvplayshot.js` | screenshots an adventure node with a mechanic part-played, which `hvshot.js` cannot do — it renders a node at rest. |
| `boxes.js` | where the note, the top bar and every choice button actually are, in scene pixels, for a given node. The pair were first placed by eye and stood squarely behind the paper note; this is how the clear column was found instead of guessed at. |
| `pageshots.js` | **look at the whole book at once.** Renders every page of the scrapbook to `.pageshots/` as its own image, so the ten collage pages can be laid side by side and compared. The book only shows one spread at a time and has no way to jump to a page, so each one is cloned into a fixed frame instead. Two traps, both already paid for: the photographs are lazy-loaded and off-screen pages never fetch them, and `cloneNode` copies the src but not the decoded bitmap — miss either and you get pages full of empty frames that do not exist in the real book, which is a very convincing way to redesign something that was never broken. Both are waited on now. |
| `pageaudit.js` | **the same book as numbers.** Per page: how much is actually used, where the weight sits, which quadrants are carrying nothing, how big the photographs are relative to each other, and how many stickers are on it. Background paper patches are counted separately from content, or a half-empty page with a big patch on it looks full. Use it with `pageshots.js` — the pictures say what is wrong, this says how far. |
| `buttons.js` | **every control on every screen, at four shapes.** Asks the three things a finger cares about and nothing else does: is the control on the screen (or inside something that scrolls far enough), is the thing under its middle the control itself rather than something laid over it, and is its HIT area at least 44px — the hit area, not the painted box, because a small chip may carry an invisible `::after` target. It found the adventure's back and quit chips at 22px tall and two buttons at 39. Note the request filter in it: every script here aborts non-localhost requests, so a blocked Google Fonts call logs an ERR_FAILED that has nothing to do with the site — only 127.0.0.1 failures count. |
| `gatefit.js` | **the front door, driven with a finger, at four shapes.** Fills the dots, refuses a wrong code, backspaces, clears, and opens the book with 2207. It exists because `buttons.js` found the gate's twelve keys at **15x15** on a landscape phone — the card is a portrait 400:700 sheet sized from the height left over, and sideways there was no height left. One thing to know before editing it: the gate checks itself 300ms after the fourth digit, so pressing Unlock after typing four races the auto-check and reads its already-cleared buffer. Three digits and the plate is how you test the plate. And a wrong code is deliberately not wiped out from under her — it shows the error, flashes the dots red and shakes the card, and clears 620ms later, so 920ms after the fourth digit. Wait for the dots to empty rather than for a number of milliseconds: a flat 1400ms wait reported the site as broken on a loaded machine where the real figure was 1076. |
| `bookfit.js` | **the book, turned page by page, at four shapes.** `pageshots.js` and `pageaudit.js` measure clones; this turns the real book and asks what a person would notice: did anything throw, is every photograph on the spread decoded, does a page hang off the screen, and is the spread one page or two. Three traps, all paid for: every page lives in `#sb-spread` all the time so counting `.sb-page` counts twelve — the ones she is looking at wear `leftpage`/`rightpage`/`solo`; view 0 is the front cover and a cover is one page in any window; and an empty photo slot walks webp, then jpg, then png, so an img that is `complete` with no pixels is mid-chain rather than broken. And the one that cost the most: **`showScreen('scrapbook')` does not start the book.** `startDioramas` does, and it is the only thing that ever calls `Scrapbook.start()`, which is the only thing that ever sets `perView` from the window. Skip it and `perView` keeps the module's initial 2 — a portrait phone then builds a two-page spread at half the page width, which reads exactly like the bug he photographed and is entirely the harness. Same shape of trap as the 3D intro in `smooth.js`: go in the way she does. |
| `revisit.js` | **going back in.** Opens the book, leaves, comes back — three times each, for the book and all four chapters — and reads the browser's own counters. Collect the garbage BEFORE reading them or it reports a leak that is not there: a chapter that rebuilds its buttons every visit leaves the old ones detached, and detached-but-collectable is not a fault. Without the collect it accused the race of +12 listeners a visit; with it, everything is +0. |
| `smooth.js` | **where the main thread stops.** Counts long tasks around each thing she does. Go in the way she does — the 3D intro waits for a tap and renders while it waits, so jumping past it with `showScreen` leaves a whole Three.js scene running behind every later measurement, which is how the first version reported a page turn as a 500ms block. And a long task counts paint: a turn profiles at ~25ms of JavaScript and still books 500ms here, because SwiftShader paints it on the CPU. What this can honestly assert is that no JS blocks. |
| `apocfit.js` | **does every card in the apocalypse fit on the screen it is drawn on?** Nothing had ever asked, and the answer was no: the overlays are sized in `cqw` — a share of the stage's width — but most of them cap the BOX at a pixel ceiling while the TYPE inside goes on scaling with the stage. On a laptop that made the hint under the wire board 31px inside a 620px card: six wrapped lines and **"step back" 35px off the bottom of the picture**, on the one puzzle the chapter asks her to solve twice. It overflowed on all five shapes tested — 42px on an iPad sideways, 45 on a phone upright, 66 on one sideways — and the television, the fridge, the radio and the note each did the same on at least one. This opens all eleven cards at five shapes and measures them against `#ap-stage`: nothing may hang off it, and every button on it must be pressable. Note the scroll rule in it — a button below the fold of a card that genuinely scrolls (the intake sheet has four rows and a stamp, and nothing would make that fit a phone held upright) is reachable and is not counted. |
| `_aplib.js` | not a test: the three things every apocalypse suite got wrong, in one place. The chapter is fetched on demand so `Apocalypse` does not exist at load; the hooks are installed behind a promise inside `start()` so `__apEnter` does not exist a line later; and Playwright's own `click` and `mouse` hang on this page, waiting for a navigation the request filter has aborted — click and drag inside the page instead. Also `goto(char)`, which finds a thing on the live grid rather than remembering where it used to be, and `skipCut()`, which runs a cut to its end the way pressing USE does so a test need not pump through all fifty-two seconds of the drive. |
| `buildcost.js` | **where the game stops dead: building a level.** `smooth.js` walks the book, the hub and the door into each chapter; it had never measured the one thing that actually freezes a phone, which is constructing a Three.js world on the main thread. **Read its output properly.** The first version reported 56 seconds for opening Super Ouissy and 50 for the roof — and that is not the game, it is `setSize`, `getContext` and `getProgramInfoLog`, WebGL driver calls that this container performs in software because it has no GPU. So what it asserts on is time in the SITE'S OWN JavaScript (frames belonging to a file in this repo), which is the part that costs the same on her phone; the software-rasteriser total is printed beside it, labelled, so nobody confuses the two again. What it found: the first level cost 1540ms of our own script, half of it painting every texture **twice** — see the `painted()` cache in apocalypse.js. Now 962ms for the first level and 400–460 for the rest, one-off per session because textures are cached. |
| `sofit.js` | **every menu Super Ouissy puts in front of her, at six shapes.** The scrollbar for the overlay (`#so-lift`) was pinned to the far LEFT edge of the stage while the card it scrolls is centred — thirty-four points of dark between them on a phone, a hundred and ten on an iPad. It read as a gold light down the side of the picture rather than as this card's bar. It is measured against the card's right edge now and may never cross the writing or leave the stage; the race had already learned the identical lesson with `.rc-rail`. The other half: a menu that fits gets no bar at all and is centred — which the title, world and pause cards already were (33/33, 45/45, 53/53), so that part needed checking rather than changing. 70 checks. Verified both ways: put the rail back on the left and every scrolling menu goes red. |
| `cutcheck.js` | **the film cannot be skipped, and there is always a way out.** Two things he asked for and one trap between them. USE used to run any finite cut straight to its end after two seconds — the drive is fifty-two of them — so one press of space threw the whole scene away; that is gone, for every cut in the chapter. And the pause button used to go out during every cut AND every line of dialogue, which between them is most of the chapter, leaving no way out but the browser's back button; it is on screen now from the first level to the end of the roof. The trap: a visible button is worthless if pressing it does nothing, and worse than worthless if the film keeps running behind the card — so this checks that a tap at its middle actually lands on it, that the card comes up, that `G.cine.t` does not move while it is up, and that the cut resumes where it stopped. One thing to know before editing it: do NOT put Escape in the list of skip attempts. Escape opens the pause card, which is a way out rather than a skip, and it left the card covering the button for every check that followed. Verified both ways: restore either old behaviour and it goes red. |
| `ostblip.js` | **the apocalypse score, as a waveform.** Nothing here had ever looked at one. He could hear "the speakers farting a blip" in the radio, the roof and the cats, and this is what it was: `line()` hands its callback `(freq, time, velocity, duration)` — the order piano, strings and bell all take — while `cello` takes `(freq, time, duration, velocity)`, the last two the other way round. Ten cues passed `cello` to `line` **bare**, so the cello got the note's DURATION as its velocity (1–3, against the 0.03 intended) and its velocity as its length: a cello at fifty times its level lasting thirty milliseconds, once a beat. Measured through the game's own chain the last cue peaked at **2.64 against a full scale of 1.0** — clipped solid for the whole of the longest scene in the game. The three cues he named are three of the ten. Fixed with one named adapter, `celloLine`. The tool renders each cue through the real chain (bus, lid, notch, shelf, master) into an OfflineAudioContext and reports peak, clicks and bottom-end level. **Note the second render with the limiter bypassed** — that is the assertion that matters: a ceiling holds almost anything under 1.0, and with it in the way this same bug measured 0.82 and passed. Verified both ways: put `cello` back and `home` reads 2.16 raw and goes red. |
| `hubfit.js` | **the hub, at the sizes she holds the phone — and it judges now.** It used to print six lines and assert nothing, which is how both of these lived there: (1) `.hub-wrap` is a centred flex column that scrolls when it must, and **a centred column that overflows pushes its top out of reach** — the scroll origin IS the top, so anything above it is unreachable by any gesture. On an iPhone SE with every chapter done, "Choose your adventure" sat 40px above the origin (53 on a small Android, 93 on a 560px screen). Fixed with `justify-content:safe center`, which centres while it fits and packs from the start when it does not, with plain `center` left above it as the fallback. (2) The hub's **"Back to the book" button carried `hub-keepsake`** — the class that hides the keepsake until the story is done — so it never appeared at all, for anyone, ever: a wired, styled door in the markup that nobody could see. Verified both ways: restore the gate and 26 checks go red; restore plain centring and 7 do. |
| `introsheet.js` | **the opening, frame by frame, and one rule about it.** `__bookCapture.frame(t)` renders a deterministic frame of the intro at a chosen second and `state()` says where the cover is and what is on the grass at that instant, so the first thing anybody sees of this site can be looked at rather than described. The rule it enforces: the left-hand page stack rests ON the opened front cover — its base sits one cover-thickness off the ground — so it may not be on screen while the cover is still in the air. It was revealed at `oe > 0.32`, which is **fifty-eight degrees**, and what appeared was a five-millimetre slab of parchment lying flat on the lawn a book's width from the spine, looking exactly like a page that had fallen out before the book was open. He photographed it. Run it with a directory to get a png per beat as well. Verified both ways: restore the old line and it goes red. |
| `padcheck.js` | The only test here that uses more than one finger. Holds a direction with one pointer id, taps jump with another, and checks she is still running — see HANDOFF 7f. Restore the old window-level `releaseAll` and it reports "jump cancelled the direction" in both orientations. |
| `trackcheck.js` | **the courses, judged as geometry.** Reads the real table and the real spline out of `racing.js` rather than a copy that would drift. Per course: lap length, race distance, tightest corner, longest straight, clearance from the edge of the world, self-crossings, whether the circuit ever doubles back and runs near itself, how hard it turns per length of road, whether the run up to the flag is straight enough to park eight karts on, and where the shortcut leaves and rejoins. Then the number the whole thing exists for — the mean distance from each point of one centreline to the nearest point of another. The road is 92 wide; the four shipped courses measured **32 to 57 apart**, which is to say they were one course in four coats. Every threshold is set just outside what those four actually measured, so a redraw has to beat them and the test cannot be satisfied by moving the goalposts. Four things to know before editing it. The straddle test compares strict opposite signs rather than `Math.sign`, because nearly-collinear samples make one cross product exactly zero and the first version reported four self-intersections in a perfect circle. The cut angle is taken over a span of samples, because at fourteen samples per control point one sample of wobble reads as a ninety-degree turn. "Doubles back" is measured by distance along the LAP, not by gap in the sample list — a spike that goes in and comes straight back out puts its two legs a handful of samples apart, and an index-gap test walks straight past the one thing it exists to catch. And the turn-per-300-units figure resamples the centreline to a fixed step first, because `catmull` steps `t` in a while loop and leaves pairs of samples almost coincident; `atan2` between two points a thousandth of a unit apart is noise, and summing it reported 600 degrees per 300 units on courses that are visibly smooth. Takes a candidate file — `node tools/trackcheck.js draft.json --map` — so a course can be drawn and read in the terminal before it is pasted into the game. |
| `racelap.js` | **the courses, driven.** Geometry does not prove a kart can get round. This opens each one and steps the game's own `step(dt)` by hand at a fixed sixtieth, running a full race in a few hundred milliseconds — it has to be by hand, because under a headless browser the clock barely advances and the starting countdown sat at three for fourteen real seconds. It flips all eight karts to the autopilot first: nobody is holding the throttle in here, so her kart would sit on the line and report the course as impassable. Asserts every kart gets round and gets home, that lap times land where a person would enjoy them, that the leader's laps are consistent, and that nobody is left behind. It also **reports** whether each shortcut is worth taking — half the grid knows about each one, which makes the field its own control group; measured through this harness the four shortcuts as they shipped came out at 1.05, 1.08, 1.04 and 1.07, meaning not one was ever worth taking. Two things it found that were not track faults at all: the autopilot aims a fixed distance up the road, so a kart knocked onto the grass drove along it parallel to the tarmac forever rather than steering back on; and the rubber-band reads `racers.find(r => r.isPlayer)` and did nothing once she was home, so the pack she had spent four laps inside came apart the moment she crossed the line. Note that the spread it measures is with the elastic off, since there is no player in this field — a lost kart still shows up, as hundreds of seconds rather than tens. Its first draft clicked `data-next="chars"` and `data-next="tracks"` in the order they are named, which starts the race before a track is chosen; four runs all came back saying Cabin Woods. |
| `panels.js` | **every panel the race puts in front of her, measured against the stage.** `landscape.js`, `buttons.js` and `handheld.js` walk the gate, the hub, the book and the games; not one of them had ever been to a results screen or a track menu, and that hole hid the worst fault the race had. The panel at the end of a round came to **512 points of a 440-point stage** with MENU, KEEP THE PHOTO and NEXT TRACK below the glass — finish a Grand Prix round and there is no way to start the next one — and it was over on an iPad (751 of 672) and a laptop (799 of 720) as well. The track grid was the other: six courses wrap to two rows where four were one row, which put START 50 points under the bottom on a landscape phone and 4-6 off on the bigger screens. Note the wait: a bigger picture takes longer to bake, so a flat timeout that suited a 440-point phone left the iPad and the laptop with no racers to finish a race with, which reads as the results panel not existing rather than as not having waited. |
| `jumps.js` | **ramps, and the one honest way to get height into a Mode 7 picture.** Mode 7 draws a flat plane: a screen row is one distance the whole way across, so a height field ends up sampling the ground under a prop at the edge of the picture at the height of the middle of it. Measured, that put the scenery fifteen pixels off its own shadow — the arithmetic is `amp × 1.37` pixels of error at the screen edge, so it is invisible only below about 1.5 units of amplitude, which is no hill at all. A flat plane seen from higher up, though, is still exactly a flat plane, so the ground stays put and the KART leaves it. This asserts the ramps exist and sit on the road where it is straight, that hitting one at speed puts her in the air and crawling over it does not, that what goes up comes down in about the time a jump should take, and that the surface stops mattering while she is off it. Two things about testing it: `step()` only counts the countdown down while the state is "count" and nothing moves until it hits zero, so a first version drove eighty frames at a ramp 130 units away and reported that ramps do not work; and the projection keeps a local hint so it does not search the whole ribbon every frame, so moving a kart in a test without moving the hint has the barrier throw it clean off the world on the next frame. |
| `stick.js` | **how the analog stick feels, as numbers.** "It doesn't feel good" is a real report and a hard one to act on, so this pins down the four things that were actually wrong with it. It was linear from zero, so a thumb resting on glass — which is never quite still — sent every tremor to the wheels and the kart hunted down a straight; there is now seven per cent of dead zone, and resting reads as exactly centred. It was linear the rest of the way too, which means a correction and a hairpin ask for the same kind of movement; the travel is now squared towards the edge, so half throw gives a third of the lock (measured 0.32) and the end of it still gives all of it. Full lock was 0.155 of the stage, which is 148 points on a 16 Pro Max — most of a hand, so it meant regripping; it is 0.115 now, 110 points. The easing has to be written `dt * 60` and not `k` — `k` is declared further down `drivePlayer` and reading it there is a temporal-dead-zone throw, which is how this file first reported itself as a crash inside `step()` rather than as a failing assertion. |
| `themes.js` | **a course with no theme, which sounds exactly like a muted game.** `playSong` is handed the track's id and returns quietly when there is no entry under it — so when two courses were added and their music was not, Harbour Lights and The Long Way Home raced in complete silence, and nothing caught it, because the one thing silence is indistinguishable from is somebody having turned the sound off. ## Do not pipe these through `tail`, and do not redirect them to a file

Node buffers its output when stdout is not a terminal, and every suite here
is long. `node mech.js | tail -30` and `node mech.js > /tmp/x.log` both show
you an empty file for the whole run and then everything at the end — so a
run you interrupt tells you nothing at all, not even which assertion it had
reached. That cost several hours in one sitting: mech.js looked wedged
through four attempts and was in fact passing assertions the whole time,
and the only reason anybody found out is that killing it flushed the buffer
and fourteen PASS lines fell out. Run bare and left alone it finishes: 27 passed, 0 failed, no page errors.

Run them bare and read the output as it comes. If you must capture it, kill
the process rather than the pipeline when you give up, because the kill is
what flushes it.

Related: on a loaded machine these run ten to twenty times slower than
normal, and `timeout` does not reliably fire, because the container's own
process clock is skewed. Judge progress by output, not by the wall clock.

## Two things that will waste your afternoon otherwise

**requestAnimationFrame runs at about 3fps in a headless container.** Any test
that waits on wall-clock time runs in slow motion and proves nothing. Set
`window.__soTestDrive = true` and advance the world with `window.__soPump(seconds, keys)`
instead — it steps the fixed timestep directly. The `__so*` hooks are
documented at the bottom of `super-ouissy.js`.

**A green suite is not a working game.** The other suites set
`window.__soTestDrive` and call `__soPump` to advance the world by hand.
That is fast and deterministic and it never once touches
`requestAnimationFrame` — so a second function declaration named `frame`,
shadowing the game loop at the same scope, made the whole game render
nothing while all 66 assertions stayed green. `realplay.js` exists because
of that: it clicks, it waits, and it reads pixels off the canvas.

**Two more that only bite the night shift.** `page.click` hangs on this
site: the page never fires `load` because every non-localhost request is
aborted, so playwright's post-click "waiting for scheduled navigations"
sits there until it times out — click through `page.evaluate` instead,
and dispatch a `pointerdown` as well as a `click`, because the office's
buttons answer to the former. And `book-scene.js` has to be kept from
loading at all: it is ACES, PMREM, bloom, bokeh and light shafts, and on
a software rasteriser it takes the main thread and does not give it
back, so everything after it times out before it can even be told to
stop.

**`page.screenshot()` hangs** while the game loop is painting: playwright waits
for the element box to be stable and never gets it. Either call
`window.__soHalt()` first and capture through CDP (`Page.captureScreenshot`),
as `screens.js` does, or pull the canvas out with `toDataURL` and skip
playwright's screenshot entirely, as `play.js` does.
